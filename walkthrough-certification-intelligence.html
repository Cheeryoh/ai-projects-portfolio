Define the work

Synthetic practitioner evidence supports proposed tasks and domain weights. A simulated reviewer disposition controls whether the JTA can feed the blueprint.

Build and set the standard

The approved simulated JTA weights constrain form assembly. Twelve simulated judges complete three Modified Angoff rounds before a separate simulated approval records the standard.

Launch and monitor

Historical data covers 10,000 synthetic attempts and 600,000 simulated item responses. Monitoring can open an investigation without changing prior scores or evidence.

Refresh and revalidate

An approved simulated revision produces a successor item. That item receives its own 500-attempt synthetic pilot and exact revalidation before a refreshed release can advance.

Program 02 · Maintain · 3:09 walkthrough

Keep a credential current after a product release.

A simulated release changes how vendor bill approval works and touches four exams. The walkthrough follows one exam item from detection to a recorded revision and a portfolio report.

16Credentials in the portfolio map
3Credential tiers
5Exams tracked in the scenario
10,000Simulated candidates

Release lands → Detect → Confirm the cause → Revise on the record → Report

01

Detect

The monitor compares each item's p-value before and after the release. A drop of at least 15 points that survives a false discovery rate correction raises a flag.

02

Confirm the cause

Item 54's p-value fell from .76 to .21, and the drop is the same at every experience level, so candidate ability did not change; the item did. A second flag with no linked release stays under monitoring.

03

Revise on the record

A human disposition revises the item. The new version sits next to the original, reported scores stand, and the revised form is not claimed as equated.

04

Report

Release impact rolls up to the portfolio: exams on track, open release-impact items, a named top risk and the credential map.

Behind the build

Agent orchestration and engineering

I designed the architecture and coordinated scoped engineering tasks through Codex and Claude Code, with defined responsibilities, review checkpoints and automated acceptance checks. The platform combines model-assisted interpretation with deterministic simulation and statistical analysis, generating thousands of candidate attempts without thousands of model calls. Versioned artifacts, reproducible runs and explicit decision gates keep the workflow auditable.

The NetSuite program runs on the same engine. It was added as a program profile and evidence package through a program registry, not as a fork of the codebase, and it deploys as its own read-only snapshot.

Both walkthroughs combine my DemoForge workflow for screen capture, timed highlights and captions with my Voicebox narration runner for resumable local narration using Voicebox.

Simulation and analysis
GPT-5.6 Luna through Codex produced a recorded investigation synthesis from analysis evidence. Seeded statistical simulation generated each 10,000-candidate population; deterministic calculations produced the metrics. The public demos replay stored model outputs and simulated reviewer decisions.
Walkthrough production
Qwen3-TTS 1.7B generated narration locally through Voicebox. Playwright captured the working applications, FFmpeg assembled the videos, and faster-whisper supplied speech-alignment checks.

Model roles: GPT-6 Astra for engineering and orchestration; Claude Opus 5.5 through Claude Code for the NetSuite program; GPT-5.6 Luna for bounded investigation synthesis; Claude Fable 5.1 for targeted code, UX and visual review. Playwright, FFmpeg and automated tests handled repeatable verification.

Engineering foundation: Node.js, TypeScript and Express; a Supabase/Postgres data model; isolated Railway demo deployments; versioned evidence, repeatable seeds and automated tests.
